## 1. 주요 결정 사항 업데이트

본 개정판은 과학 MEF 정책을 CCD 단위 원시 산출물에서 64증폭기 L0 원시 산출물로 변경한다. 이 변경은 자료 처리(data reduction) 요구사항에서 비롯되었다. 즉, 완전한 CCD 영상을 구성하기 전에 증폭기 단위의 오프셋, 오버스캔, 게인, 읽기 잡음, 크로스토크, 바이어스 점프, 경계 천체 효과를 먼저 보정해야 하기 때문이다.

- 주 원시 아카이브 및 보정 입력 자료는 L0 64증폭기 MEF로 한다.
- 각 증폭기 확장은 해당 증폭기의 국소 유효 픽셀과 국소 오버스캔 픽셀을 그대로 보존해야 한다.
- CCD 단위 SCI_M, SCI_K, SCI_N, SCI_T 영상은 증폭기 단위 보정을 완료한 뒤에만 생성한다.
- MKNT 순서는 검증된 Archon 컨트롤러 그룹핑과 기존 변환기 처리 흐름을 따르므로 그대로 유지한다.

| 산출물 레벨 | MEF 이미지 구성 | 주요 용도 | 상태 |
| --- | --- | --- | --- |
| L0 원시 | 64개 증폭기 확장 + 바이너리 테이블 | 원시 아카이브, 오버스캔/바이어스/게인/크로스토크 보정, 디버깅 | 주 원시 산출물 |
| L1 보정 | SCI_M, SCI_K, SCI_N, SCI_T + 보정 이력 | 천체측정, DIA, 측광용 보정 CCD 영상 | 파생 산출물 |
| L2 과학 | 차감 영상, 카탈로그, 광도 곡선 | 과학 분석 결과물 | 파이프라인 산출물 |

## 2. 검증된 Archon 원시 데이터의 기하 구조

실제 Archon 시험 파일은 과학 원시 데이터가 두 개의 파일로 구성되는 구조를 보인다. MK 파일은 M 칩과 K 칩의 데이터를 담으며 관측 메타데이터의 주 출처이다. NT 파일은 N 칩과 T 칩의 데이터를 담는다.

> **v4.1 변경 (OI-8).** v4.0 은 검증 시점 표본을 근거로 NT 파일이 *"FITS 헤더에는 최소한의 정보만 들어 있을 수 있다"* 고 기술했다. **이는 더 이상 허용되지 않는다.** **MK·NT 두 파일 모두** [`../KMT_CEU_Raw_FITS_Pair_Spec_v1.2.md`](../KMT_CEU_Raw_FITS_Pair_Spec_v1.2.md) 5장이 정한 **필수 헤더 전량을 실어야 한다.** 근거 셋 — (1) NT 파일이 그 자체로 해석 가능해야 완전한 아카이브 자산이 된다, (2) 컨트롤러 2의 정체성·텔레메트리는 NT 헤더에만 존재한다, (3) pair 일관성 검사는 양쪽에 같은 keyword 가 있어야 성립한다.

| 원시 파일 | 포함 칩 | 역할 |
| --- | --- | --- |
| `<SITE>.YYYYMMDD.NNNNNN.MK.fits` | M, K | 주 메타데이터 원본이자 픽셀 데이터 원본 |
| `<SITE>.YYYYMMDD.NNNNNN.NT.fits` | N, T | 픽셀 데이터 원본. **필수 헤더 전량 필요** (v4.1 — v4.0 의 "최소한만 존재할 수 있음" 은 폐기) |

| 항목 | 검증된 값 | 해석 |
| --- | --- | --- |
| RAWNAX1 | 19200 | X 방향으로 1200픽셀 증폭기 타일 16개 |
| RAWNAX2 | 9400 | 하단 유효 행 4616 + 중앙 Y 오버스캔 168 + 상단 유효 행 4616 |
| RAWXTILE | 1200 | 유효 열 1152 + 오버스캔 열 48 |
| AMPDATA | 1152 | 증폭기 타일당 유효 열 수 |
| OVERSCNX | 48 | 증폭기 타일당 국소 X 오버스캔 열 수 |
| PRESCANX | 0 | 검증된 Archon 원시 데이터에는 국소 X 프리스캔이 없음 |
| MIDOVSCY | 168 | 하단과 상단 유효 영역 사이의 중앙 Y 오버스캔 행 |

### 2.1 원시 파일명 (v4.1, D-011)

원시 pair 파일명의 prefix 는 v4.0 의 고정 문자열 `KMTN` 을 대신해 **4자 대문자 사이트 코드**를 쓴다. 이 사이트 코드는 **TC 텔레메트리 `TELID` 규약과 같으므로**, 새 식별자가 아니라 기존 식별자의 파일명 확장이다.

```text
<SITE>.<YYYYMMDD>.<NNNNNN>.MK.fits
<SITE>.<YYYYMMDD>.<NNNNNN>.NT.fits
```

| `<SITE>` | 사이트 | `OBSERVAT` 헤더 | L0 MEF prefix |
| --- | --- | --- | --- |
| `KMTC` | CTIO | `CTIO` | `kmtc` |
| `KMTS` | SAAO | `SAAO` | `kmts` |
| `KMTA` | SSO | `SSO` | `kmta` |
| `KMTT` | 테스트베드 (실험실·데모·Full Rehearsal) | `TESTBED` | `kmtt` |

- `<YYYYMMDD>`: 8자리. 관측 야간 기준 날짜.
- `<NNNNNN>`: 노출 일련번호. **6자리 고정폭, 0으로 좌측 패딩.** pair 양쪽이 같은 값이어야 한다.
- 접미 `.MK.fits` / `.NT.fits` 는 **대소문자까지 정확히** 일치해야 한다. 변환기가 이 문자열로 짝을 찾는다.
- 파일명의 `<SITE>` 는 헤더 `OBSERVAT` 와 일치해야 한다. 변환기(v2.2.0)는 출력 MEF prefix 를 파일명 사이트 코드에서 유도하고 `OBSERVAT` 와 교차 검증해 불일치를 오류로 처리한다.
- OBSAgent 로 나가는 `Wrote` **논리 이름은 레거시 `KMTN<chip>` 형태를 그대로 유지하며 이 변경의 영향을 받지 않는다** (DECISION_LOG D-010/D-011).
- 근거·매핑 권한·실패 양상: [`../KMT_CEU_Raw_FITS_Pair_Spec_v1.2.md`](../KMT_CEU_Raw_FITS_Pair_Spec_v1.2.md) 2.3절 및 DECISION_LOG D-011.

## 3. 칩 순서 및 증폭기 번호 체계

본 ICD의 공식 과학 칩 순서는 M, K, N, T이다. 이는 원시 파일의 그룹핑과 변환기의 반복 처리 구조를 따른 것이다.

| 칩 | 원시 출처 파일 | 전역 증폭기 번호 범위 | 이미지 확장 순서 |
| --- | --- | --- | --- |
| M | MK | 1–16 | M01T..M08T, M01B..M08B |
| K | MK | 17–32 | K01T..K08T, K01B..K08B |
| N | NT | 33–48 | N01T..N08T, N01B..N08B |
| T | NT | 49–64 | T01T..T08T, T01B..T08B |

`CHIPLIST = 'M,K,N,T'` · `RAWGROUP = 'MKNT'` · M: AMPID 1–16 / K: 17–32 / N: 33–48 / T: 49–64

## 4. 기존 OSU 방향 규약과 CEU Archon 방향 규약

기존 OSU 전자계에서는 M/T와 K/N을 서로 다른 방향 그룹으로 취급해 왔다. CEU Archon 시스템에서는 모든 과학 CCD를 동일한 상/하 양단 읽기 방식으로 읽으며, L0 패킹 단계에서 OSU 방식의 칩별 영상 반전을 적용하지 않는다.

| 항목 | 기존 OSU 카메라 | KMT-CEU Archon L0 |
| --- | --- | --- |
| 칩별 영상 반전 | M/T와 K/N 방향 그룹이 존재했음 | 칩별 반전 없음. `CHIPFLP=None` |
| Y 방향 구분 | 칩 그룹에 따라 달라질 수 있었음 | TOP/BOT 단자에만 의존 |
| TOP/BOT 매핑 | 기준이 되는 규약이 아니었음 | 모든 칩에서 증폭기 1–8 = TOP, 증폭기 9–16 = BOT |
| 원시 아카이브 요구사항 | 과거의 스트립/증폭기 관례 | 64개 증폭기 확장과 AMPINFO를 명시 |

## 5. L0 64증폭기 MEF 구조

L0 원시 MEF는 각 증폭기를 하나의 이미지 확장으로 저장한다. 각 증폭기 영상은 1200 × 4616 픽셀이며, 유효 열 1152개와 국소 오버스캔 열 48개를 포함한다. 이를 통해 증폭기 단위 보정을 직접적이고 재현 가능하게 수행할 수 있다.

```text
PRIMARY
M01T M02T M03T M04T M05T M06T M07T M08T
M01B M02B M03B M04B M05B M06B M07B M08B
K01T ... K08T, K01B ... K08B
N01T ... N08T, N01B ... N08B
T01T ... T08T, T01B ... T08B
AMPINFO
XTALKINFO
VOLTINFO
TELEMETRY
```

| 확장 종류 | NAXIS1 | NAXIS2 | 내용 |
| --- | --- | --- | --- |
| 증폭기 이미지 확장 | 1200 | 4616 | 유효 픽셀과 국소 오버스캔을 포함한 증폭기 절반 스트립 1개 |
| AMPINFO | — | — | 64행으로 구성된 증폭기 기하/전자계 기준 맵 |
| XTALKINFO | — | — | 64 × 64 크로스토크 모델 테이블. 초기에는 보정값이 임시값일 수 있음 |
| VOLTINFO | — | — | 바이어스 및 클록 전압 설정값/텔레메트리 |
| TELEMETRY | — | — | Archon 컨트롤러 상태 및 읽기(readout) 텔레메트리 |

## 6. L0가 64개 증폭기 영상을 보존해야 하는 이유

핵심 이유는 파일 크기가 아니라 **측광 정확도**이다. 증폭기 단위 보정을 하기 전에 원시 데이터를 4개의 CCD 영상으로 조립하면 증폭기 경계의 불연속이 PSF/DIA 측광을 오염시킬 수 있으며, 특히 밀집 영역에서 그 영향이 크다.

- 증폭기 오프셋은 각 증폭기의 국소 오버스캔을 이용해 측정하고 보정해야 한다.
- 게인과 읽기 잡음의 차이는 증폭기 고유의 특성이므로 CCD 조립 전에 적용해야 한다.
- 크로스토크와 바이어스 점프는 전자계에서 기인하는 현상이므로 증폭기 좌표계에서 진단하는 것이 가장 효과적이다.
- 천체가 증폭기 경계에 걸쳐 있는 경우, 오프셋을 보정하지 않으면 PSF가 왜곡되어 잘못된 플럭스가 산출될 수 있다.
- 밀집 영역의 DIA 및 PSF 측광은 증폭기 단위 보정이 모두 끝난 뒤의 CCD 영상에 대해 수행해야 한다.

| CCD 단위로 원시 데이터를 저장할 때의 위험 | 결과 | 64증폭기 L0의 해결 방식 |
| --- | --- | --- |
| 증폭기 경계가 SCI 영상 내부에 가려짐 | 경계 오프셋 보정이 간접적이고 불안정해짐 | 확장과 AMPINFO를 통해 경계가 명시됨 |
| 국소 오버스캔이 제거되거나 분리됨 | 바이어스 추적이 어려워짐 | 각 증폭기 확장 안에 오버스캔이 그대로 유지됨 |
| 천체가 두 증폭기에 걸쳐 있음 | 오프셋이 서로 다르면 PSF/배경이 부정확해짐 | 각 증폭기를 먼저 보정한 뒤 CCD 영상을 조립 |
| 전자계 인공 신호(artifact) 진단 | 근본 원인이 가려질 수 있음 | 인공 신호가 AMPID/CTRLID/CHANNEL과 계속 연결됨 |

## 7. 증폭기 확장의 영역(section) 정의

각 L0 증폭기 확장의 국소 영상 좌표계는 1200 × 4616이다. `DATASEC` 과 `BIASSEC` 은 해당 확장 내부의 국소 좌표이며, `CCDSEC` 과 `DETSEC` 은 동일한 픽셀을 CCD 좌표계 및 모자이크 좌표계로 매핑한다.

| 증폭기 그룹 | 국소 DATASEC | 국소 BIASSEC | 의미 |
| --- | --- | --- | --- |
| 증폭기 1–4 및 9–12 | `[1:1152,1:4616]` | `[1153:1200,1:4616]` | 오버스캔이 오른쪽에 위치 |
| 증폭기 5–8 및 13–16 | `[49:1200,1:4616]` | `[1:48,1:4616]` | 오버스캔이 왼쪽에 위치 |

| 증폭기 범위 | ENDID | CCDSEC Y 범위 | 원시 Y 출처 |
| --- | --- | --- | --- |
| 1–8 | TOP | 4617:9232 | 4785:9400 |
| 9–16 | BOT | 1:4616 | 1:4616 |

## 8. AMPINFO 바이너리 테이블

AMPINFO는 이미지 확장을 원시 픽셀 출처, CCD 좌표, 검출기 모자이크 좌표, 전자계 채널 식별 정보와 연결하는 기계 판독 가능한 기준 맵이다.

| 컬럼 그룹 | 대표 컬럼 | 목적 |
| --- | --- | --- |
| 식별 정보 | EXTNAME, AMPID, CHIPID, STRIPID, ENDID, AMPNAME | 각 증폭기 확장을 식별 |
| 원시 출처 | RAWFILE, RAWDATA, RAWBIAS | MK/NT 원시 파일에서 정확한 원본 픽셀을 추적 |
| 기하 정보 | CCDSEC, AMPSEC, DETSEC, DATASEC, BIASSEC, TRIMSEC | 국소 좌표, CCD 좌표, 검출기 좌표 간 매핑 |
| 전자계 정보 | CTRLID, MODULE, CHANNEL, XTALKGROUP | 증폭기를 컨트롤러 및 전자계 체인에 매핑 |
| 보정 정보 | GAIN, RDNOISE, SATLEVEL, LINMAX | 증폭기 단위 보정 파라미터 저장 |
| 방향 정보 | CHIPFLP, READDIR, STRIPDIR | CEU 방향 규약 기록 |

## 10. 권장 처리 순서

1. L0 64증폭기 MEF와 AMPINFO를 읽는다.
2. `BIASSEC` 을 이용해 각 증폭기 확장에 국소 오버스캔 보정을 적용한다.
3. 증폭기 단위의 바이어스, 게인, 읽기 잡음, 선형성, 포화, 불량 픽셀 마스크를 적용한다.
4. 계수 보정이 완료된 뒤 XTALKINFO를 이용해 크로스토크 보정을 적용한다.
5. 증폭기 경계의 이음매와 바이어스 점프 흔적을 점검한다.
6. 보정된 SCI_M, SCI_K, SCI_N, SCI_T CCD 영상을 조립한다.
7. 천체측정, DIA, PSF 측광, 카탈로그 매칭, 광도 곡선 생성을 수행한다.

## 11. 변환기 구현 현황

함께 제공되는 변환기(`kmt_ceu_archon_mknt_to_l0_amp_mef_v2_1.py`, **v2.2.0**)는 검증된 MK/NT 원시 영상으로부터 L0 64증폭기 MEF 구조를 생성한다. 64개의 증폭기 이미지 HDU와 필수 바이너리 테이블 4개를 만든다. **v2.2.0 부터는 출력 prefix 를 파일명 사이트 코드에서 유도하고 `OBSERVAT` 와 교차 검증한다**(2.1절).

```bash
python kmt_ceu_archon_mknt_to_l0_amp_mef_v2_1.py \
  KMTA.20260116.000001.MK.fits \
  -o kmta.20260116.000001.ceu.l0amp.mef.fits \
  -f --gzip
```

| 생성 파일 | 설명 |
| --- | --- |
| `kmta.20260116.000001.ceu.l0amp.mef.fits` | 전체 크기의 L0 64증폭기 MEF 샘플 |
| `kmta.20260116.000001.ceu.l0amp.mef.fits.gz` | 전송용 압축 사본 |
| `kmt_ceu_archon_mknt_to_l0_amp_mef_v2_1.py` | 본 ICD 개정판을 구현한 변환 스크립트 |
| `*.summary.txt`, `*.hdu_verify.txt` | 변환 및 HDU 검증 요약 파일 |

## 12. 미결 사항 및 주의점

- `READDIR` 은 임시 규약으로 TOP=−Y, BOT=+Y로 기록되어 있다. 최종 방향은 플랫/별상 연속 촬영 시험으로 확인해야 한다.
- 현재 샘플의 XTALKINFO 값은 임시값이므로 실제 보정 계수로 사용해서는 안 된다.
- 원시 헤더에 실제 Archon 텔레메트리가 없는 경우 VOLTINFO와 TELEMETRY는 임시값이다. **필요한 원시 헤더 텔레메트리 집합은** [`../KMT_CEU_Raw_FITS_Pair_Spec_v1.2.md`](../KMT_CEU_Raw_FITS_Pair_Spec_v1.2.md) **5장에 정의돼 있다.**
- L1 CCD 단위 영상은 증폭기 단위 보정과 이음매 검증을 마친 뒤에만 생성해야 한다.
- L0 산출물은 CCD 단위 산출물보다 크고 복잡하지만, 정밀 측광과 장기 재처리에는 더 적합하다.
- **D-011 이전에 만들어진 표본 pair 는 검증 기록상 `KMTN.*` 이름을 유지한다.** 변환기 v2.2.0 의 기본 동작으로 다시 돌릴 때는 pair 양쪽을 사이트 코드 형식으로 개명해야 한다.
