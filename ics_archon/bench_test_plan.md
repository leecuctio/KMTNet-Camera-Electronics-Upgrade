잘 남겨줘"*).

이 문서는 **무엇을 어떤 순서로 재고, 무엇이 있어야 잴 수 있고, 어떤 값이 나오면 무엇이 닫히는가**를

## 0단계 — 시작 전 준비물 ⚠️ **없으면 1단계가 막힌다**

### (a) RADIONODE 자격증명 — ⛔ **운영자만 할 수 있다** (콘솔 접근)

코드가 대신 못 하는 것 넷이다 (DevNote 2266, 9.7):

| # | 준비물 | 어디서 |
|---|---|---|
| 1 | **계정 등급** — Open API 를 쓸 수 있는 등급인가 | Tapaculo365 콘솔 |
| 2 | **API KEY / SECRET** + OPENAPI 매뉴얼의 **base URL · 경로 · rate limit** | 관리자 이름 → 고객사 정보 변경 → API KEY/SECRET |
| 3 | **사이트 LoRa 게이트웨이 기종** (사설 LNS 경로가 가능한지 판단용) | 현장 확인 |
| 4 | **장치 SEND INTERVAL** 결정 — 1분은 배터리가 닳는다, **2~5분 절충 권장** | 콘솔 |

⛔ **KEY/SECRET 실값을 저장소 `icg_archon.ini` 에 적지 말 것.**  한 번 커밋되면 이력 재작성 없이는
못 뺀다.  **벤치 설치본 `~/AIC/etc/icg_archon.ini` 에만** 적는다.  절차는 `README.md` 의
"Radionode 자격증명" 절.

⛔ **`stale_after` 가 재는 것은 장치의 표본시각이 아니라 우리가 폴링을 받은 시각이다** (2026-09-06 확인) -- `_store()` 가 그 자리에서 `time.monotonic()` 을 찍고, 응답의 시각 필드를 읽는 코드가 없다.  그래서 이 값이 잡는 것은 **장치 침묵이 아니라 폴링 실패**(인터넷·API 장애)뿐이고, `HKUDATE` 도 측정시각이 아니라 **마지막 폴링 성공 시각**이다.
⛔ **게다가 헤더 경로에서는 아무 일도 안 한다** -- `sensors()` 의 지평선 `interval*3`(기본 **180 s**)이 먼저 자르므로 600 s 는 헤더에 닿지 않는다.  세 문턱이 따로 논다: `radionode.stale_after` 600 → `hk.sensors()` 180 → science `hk_stale_after` 300.

⭐ `stale_after` 는 **SEND INTERVAL 의 약 3배**로 맞춘다 (현재 600 s = 3분 간격 전제 -- ⚠️ 3×180 s = 540 이지 600 이 아니다).  ④를 정하면
이 값도 함께 고친다 — 안 고치면 멀쩡한 표본을 낡았다고 버리거나, 낡은 값을 헤더에 싣는다.

### (b) 그 밖

- 벤치 네트워크에서 **인터넷이 되는가** — `openapi` 백엔드는 인터넷이 있어야 한다.  끊기면
  `HEBOX`/`FSATEMP`/`FSAHUM` 이 그동안 sentinel 이고, 운영자는 그 결측을 받아들이지 않는다(2026-09-04).
- guide 유닛 `10.0.0.162` 접속 · ACF **`KMTK_GUI_162_STA0201_R2617.acf`** 적용 여부.
- science 는 **`KMT?_SCI_*_R2611_*.acf`** 6장이 현행이다.
- ⭐ **장치 MAC / 시리얼** — 벤치 ini 의 `[radionode.hebox]`·`[radionode.fsa]` 에 적을 값.
  ⚠️ 자격증명 넷과 **별개**다.  이것이 어긋나면 3(`CONNECT`)은 통과하는데 4(`HK`)에서
  값이 계속 sentinel 로 남아, 원인을 "인터넷/계정 등급" 으로 오진하기 쉽다.
- **`stale_after`** = 장치 SEND INTERVAL 의 **3배** 로 맞춘다 (0단계 (a) 4번에서 정한 값).

### (c) ⛔ 배포 ini 그대로면 **ICS 가 기동에서 멈춘다** (2026-09-06 전수 검토)

네 가지가 실기 기동 앞을 막거나 조용히 어긋난다.  **전부 코드로 확인했다.**

| # | 무엇 | 근거 | 해야 할 것 |
|---|---|---|---|
| 1 | ⛔ **`ics_archon` 이 기동에서 죽는다** | 배포 `ics_archon.ini` 가 `require_xis = true`(274행) 인데 `xis_host` 는 **비어 있다**(44행).  `xischeck.py:100` 이 `XisUnreachable` 을 던진다 | 벤치 ini 에서 **`xis_host` 를 적거나 `require_xis = false`** 로.  ⛔ 코드는 자동으로 직결로 안 넘어간다 (11.15 확정) |
| 2 | ⚠️ **ICS 는 허브를 요구하는데 ICG 는 안 쓴다** | `require_xis`·`XisGate` 는 `[archon]` 소관이라 **ICG 에 아예 없다**(`grep` 0건).  `icg_archon.ini:37` 은 `#xis_host` 주석 = direct-reply | 둘을 **같은 모드로** 맞춘다.  안 맞추면 `ICS→ICG` 의 `VACGAUGE OFF`·`HKDATA` 가 허브에서 버려진다 |
| 3 | ⛔ **`~/AIC/etc/…` 는 아무도 안 읽는다** | `DEFAULT_INI = 'ics_archon.ini'` — **실행 디렉터리 기준 상대경로**다.  `~/AIC/etc` 를 읽는 코드가 `grep` 0건 | 자격증명을 그 파일에 적었으면 **`-c ~/AIC/etc/icg_archon.ini` 로 명시**하거나 그 디렉터리에서 실행한다.  안 그러면 `RADIONODE CONNECT` 가 *"자격증명 없음"* 으로 거절하고, 운영자는 **콘솔 값이 틀린 줄 오해한다** |
| 4 | ⚠️ **짝이 안 맞는 ACF 는 `IP=` 까지 밀어 넣는다** | ACF 안에 `IP=10.0.0.162`(guide)·`IP=10.0.0.113`(science)가 있고, `apply_acf()` 는 **전 키를 `WCONFIG`** 한다 — `IP` 를 거르는 코드가 없다 | 유닛과 ACF 짝을 **적용 전에 눈으로** 대조한다.  ⚠️ `APPLYALL` 만으로 IP 가 바뀌지는 않는 것으로 보이나(`APPLYNET` 이 따로다) **확인된 바 없다** — `FLASHACTIVECONFIG`·`REBOOT` 가 뒤따르면 굳는다 |

⭐ **1·2 는 한 줄로 정리된다** — 첫 구동은 **둘 다 허브 없이**(ICS `require_xis = false`,
ICG `xis_host` 비움) 돌려 취득 경로만 가르고, 허브 연동은 그 뒤에 **둘을 함께** 붙인다.

## 1단계 — RADIONODE 자료획득 시험 ⭐ **다음 세션 첫 항목**

> ⛔⛔ **기동이 곧 전원 인가다** (2026-09-06 정정 — 종전 문구가 거짓이었다).
> `ArchonController.prepare()` 끝이 `if not self.powered: await self.power_on()` 이고,
> ICG 기동의 `_connect_controller()` → `guide.prepare()` 가 그것을 부른다.  즉
> **실기 백엔드로 `python3 -m icg_archon` 을 띄우는 순간 `CLEARCONFIG`+`WCONFIG`
> 전량+`APPLYALL`+`POWERON` 이 돈다** (`apply_acf = true`).
>
> ⭐ **그래서 1단계를 돌리는 길이 둘이다:**
>
> * **(가) 전원 없이** — `--backend sim` 으로 띄운다.  `SimGuideBackend` 라 컨트롤러
>   접속 자체가 없어 Radionode 배선만 가른다.  ⚠️ 헤더 경로는 못 본다.
> * **(나) 실기로** — [`icg_first_run.md`](icg_first_run.md) **0~2단계를 먼저**
>   마친다(배선 · probe · **Config 슬롯 대조**).  ⛔ 슬롯 대조를 건너뛰고 기동하면
>   `set_config` 가 엉뚱한 줄을 고쳐 `EXPTIME` 이 조용히 안 바뀐다.
>
> 아래 절차 1~5 는 헤더가 필요 없다 — 위 (가)면 전원 없이 그대로 돌릴 수 있다.
> ⛔ **헤더를 봐야 하는 항목(구 6·7·8)은 `1-B` 로 갈랐다** — 그것은 `go 1`,
> 곧 **첫 전원 인가**를 요구하므로 [`icg_first_run.md`](icg_first_run.md)
> **0~4단계를 먼저 마쳐야 한다**.

**닫히는 것**: 규격 `OI-16`(Radionode 원값 포맷) · 5.8절 *"원값 그대로 싣기"* 확정 · HK 5장 중
`HEBOX`/`FSATEMP`/`FSAHUM` 의 실기 경로.

### 절차

| # | 하는 것 | 기대 | 실측 |
|---|---|---|---|
| 1 | 벤치 ini 에 자격증명 4개를 적고 ICG 기동 | 기동 로그에 Radionode 폴러가 뜬다 | |
| 2 | `RADIONODE STATUS` | 폴링 상태 + 장치 둘(`hebox`·`fsa`)의 접속 상태 | |
| 3 | (ini 가 `off` 였다면) `RADIONODE CONNECT` | `off` → `openapi` 로 올라가고 폴링 루프가 뜬다. ⚠️ 자격증명이 모자라면 **무엇이 없는지 대고 거절**한다 | |
| 4 | 1~2 폴링 주기 기다린 뒤 `HK` | `HEBOX=` `FSATEMP=` `FSAHUM=` 이 **실값**으로 보인다 (sim 고정 상수가 아님) | |
| 5 | ⭐ **원값 포맷을 그대로 적어 둔다** | Open API 응답의 원문 표기(소수 자리·부호·단위) — 이것이 `OI-16` 의 답이다 | |

### 판정 (1단계)

- **통과**: 4 가 실값이고 5 에 원값 표기를 적어 왔다.
- **멈출 조건**
  - 3 에서 자격증명 거절 → 0단계 (a) 로 돌아간다.
  - ⭐ **3 은 통과했는데 4 가 계속 sentinel** → 0단계 (a) 로 통째로 돌아가지 말 것.
    장치 **MAC/시리얼**이 ini 의 `[radionode.hebox]`/`[radionode.fsa]` 와 맞는지,
    `stale_after` 가 **SEND INTERVAL 의 3배**인지부터 본다 (그 둘이 준비물 표에 없어
    실제로 여기서 막힌다).
  - 폴링이 아예 안 뜨면 `RADIONODE STATUS` 의 `backend=` 를 본다 — 기본이 `off` 다.

### ⏳ 실험하면서 함께 볼 것 -- Radionode 가 값을 버리는 자리 넷

운영자 2026-09-06: *"Radionode는 실험해 보면서 하나씩 확인/업데이트 하자."*
실측 보존 감사가 찾은 자리다.  **지금 고치지 않고 실험 중에 하나씩 판단한다** --
실기 응답 모양을 아직 아무도 못 봤기 때문이다 (`radionode.py` 스스로 PROVISIONAL 이라 적어 뒀다).

| # | 무엇을 버리나 | 어디 | 실험 중에 볼 것 |
|---|---|---|---|
| 1 | **응답의 첫 수치 하나만 집고 나머지를 안 남긴다** -- 배터리·RSSI·다른 채널·장치 시각이 `_latest` 에도 CSV 에도 파일에도 없다 | `_pick()` / `_store()` | ⭐ **5번 걸음에서 원값 포맷을 적을 때 응답 전문을 함께 파일로 남길 것.**  그것이 이 판단의 자료다 |
| 2 | **NS 코덱이 없어 해석값이 없으면 base64 원문까지 버린다** | `take_uplink()` | 나중에 코덱을 올려도 **그 기간은 소급 복원이 안 된다.**  설치 초기 며칠이 통째로 빌 수 있다 |
| 3 | **ini 에 없는 DevEUI 는 세기만 하고 payload 를 버린다** | 〃 | 센서를 더 달고 ini 에 안 적은 동안의 실측이 사라진다.  ⭐ 다만 수는 세므로 `RADIONODE STATUS` 로 *"왜 안 들어오나"* 는 보인다 |
| 4 | **`DISABLE` 된 장치의 uplink 를 로그도 카운터도 없이 버린다** | 〃 | ⚠️ 운영자는 `DISABLE` 을 *"헤더에 안 싣기"* 로 읽기 쉬운데 실제로는 **"기록조차 안 하기"** 다.  명령 응답 문구에도 그 차이가 없다 |

⭐ **`stack.pop()` 은 역순이다** -- 이력 배열이 오면 *"마지막 원소부터"* 집는다.  이것만은
코드에서 확정이니, 응답에 배열이 들어 있으면 **어느 표본을 집었는지** 5번 걸음에서 확인할 것.

### 판정 (1-B)

- **통과**: 1·2 가 실값이고 3 이 sentinel 로 정확히 떨어진다.
- **멈출 조건**: 1 에서 부호 규약이 어긋나면 `rawhdr.format_temp`/`format_ens` 를 먼저
  본다(규격 5.0 · 5.8).  ⛔ `POWERON` 이 `?xx` 로 거절당하면 (⚠️ **첫 `go` 가 아니라 기동 로그**에 뜬다 — `apply_acf=true` 면 기동이 이미 전원을 켠다.  `app.py` 가 그 실패를 로그로만 남기고 기동은 계속한다) **Apply All 이
  없었던 것**이다 — 다시 돌리지 말고 `icg_first_run` 0단계로 돌아간다.
- ⚠️ `sim` 백엔드는 고정 상수를 내고 **헤더 경로로는 안 나간다** — 배선 확인용이지 이 시험의 답이 아니다.

## 2단계 — guide 첫 구동 실측 [ICG]

절차는 [`icg_first_run.md`](icg_first_run.md) 0~6단계 그대로.  이 문서는 **그 표에서 닫히는 미결**만
짚는다.

| 항목 | 쪽 | 준비물 | 판정 | 닫히는 것 |
|---|---|---|---|---|
| `RESETTIMING` 뒤 파라미터 RAM 보존 | ICG | `abort` 한 번 | abort 뒤 flush 가 **정확히 한 번** 돌면 RAM 이 보존된 것 | DevNote 11.32-(1) ⏳ |
| `go 1` 뒤 FRAME 카운터 +1 | ICG | `go 1` | 카운터 증가분이 **1** (flush 는 프레임을 안 만든다) | `OI-26` |
| **STOP 뒤 꼬리 flush** | ICG | `go 5` 중 `stop` | 마지막 저장 뒤 `FRAME` 불변 + **≈1.25 s 클록** 한 번 | DevNote 11.33-(1) ⏳ |
| 기본 노출시간 실측 | ICG | ⛔ **`guideexp 1.3` 으로는 못 잰다** -- 벤치 ini 의 `[icg] exptime_min` 을 **1.0** 으로 내리고 `guideexp 1.0` | ⭐ 그때 `IntMS=0` 이라 **주기가 곧 기본 노출시간**이다.  `1.2506 s` 계산값과 몇 % 안에 드나 | `acftiming` PROVISIONAL 해제 |

### ⛔ 히터 강제 출력 — 안전 봉투 (`OI-28` 실측용)

⚠️ **`HTRFORCE 1` 은 PID 를 우회한다** — `HEATERALIMIT`(25 V)은 **PID 모드 전용**이라
강제 모드에서는 안 걸린다.  즉 **온도와 무관하게 지시한 전압이 그대로 나간다.**
⭐ 코드에 운영 상한(`heater_force_max`)을 **일부러 두지 않았으므로**(값 미정, DevNote
11.14-(3)) **그 상한이 사는 자리는 이 문서뿐이다.**

⭐ **전제 — `FORCE=0` 이면 출력이 꺼진다 (0 V).**  근거 등급은 **운영자 확정
(2026-09-06)** 이다 — 매뉴얼(p.60-61)은 `FORCELEVEL` 의 범위(`0.000~25.000 V`)만 적고
*`FORCE=0` 일 때 레벨이 출력에 물리는지는 한 줄도 없다.*  ⚠️ 실측으로 확인된 것이
아니므로, 이 전제가 깨지는 관찰(예: `FORCE=0` 인데 `HTROUT` 이 0 이 아니다)이 나오면
**그 자리에서 멈추고 기록할 것.**

⭐ **자동 차단이 하나 생겼다** (2026-09-06 신설, `heater.OverTempGuard`) — 되먹임 센서
(`HEATERASENSOR` → `SENSORA`=`RTD9_DMP`)가 ACF 의 `SENSORAUPPERLIMIT`(현행 **50.0 °C**)를
넘으면 `FORCE`·`FORCELEVEL`·`ENABLE` 셋을 0 으로 쓴다.  ⚠️ **빠른 인터록이 아니다** —
판정이 HK 루프 주기로만 돌아 최대 `[hk] interval` 만큼 늦고, 50 °C 는 DMP 운전점
(−120 °C)에서 한참 위다.  **이 문서의 절차가 여전히 1차 방어선이다.**

⭐ **지금 히터가 안 붙어 있다** (운영자 2026-09-06) -- 그래서 둘로 가른다.  **A 는 지금
벤치에서 할 수 있고**(열이 갈 데가 없어 위험 0), B 는 히터를 연결한 뒤(SSO 설치 후)다.

#### A. 무부하 확인 -- ⭐ **지금 할 수 있다** (히터 미연결)

⭐ 운영자 착안: *"그냥 STATUS HEATEROUTPUT 을 보면 되지 않을까?"* -- 맞다.  부하가 없어도
`MOD10/HEATERAOUTPUT` 은 읽히므로 **`FORCE` 게이팅과 `OI-28` 을 같은 왕복으로 좁힌다.**

⚠️ `HK` 는 60초 캐시라 여기 쓰지 마라.  `archon STATUS` 로 직접 읽는다 -- 응답이 1800 B
에서 잘리므로 **전문은 `icg_archon.cmd` 로그**에서 본다.

| # | 명령 | 보는 것 | 실측 |
|---|---|---|---|
| A1 | `HTRSET` (인자 없이) | 현재 `Enable=…  Target=…` 을 **적어 둔다** (A7 복귀용) | |
| A2 | `HTRSET 0 <A1 의 목표온도>` | Enable 을 끈다.  인자는 **정확히 둘**이다 | |
| A3 | `HTRFORCE 0 2.0` | ⭐ **`FORCE=0` 인데 레벨만 2.0.**  `archon STATUS` 의 `MOD10/HEATERAOUTPUT` | |
| A4 | **판정** | `0.000` → `FORCE=0` 이 출력을 막는다 (운영자 이해와 일치) · **`~2.0` → ⛔ 막지 않는다** | |
| A5 | `HTRFORCE 1 2.0` | 같은 필드.  ⭐ **`2.000` 딱** 이면 명령값 쪽 · **`1.9xx`** 처럼 어긋나면 측정값 쪽 (`OI-28`) | |
| A6 | ⛔ `HTRFORCE 0 0` | `MOD10/HEATERAOUTPUT` 이 `0.000` 인지 확인 | |
| A7 | `HTRSET <A1 의 Enable> <A1 의 목표온도>` | 정상 제어로 복귀 | |

⚠️ **A4 의 `0.000` 은 약한 증거다.**  `HEATERAOUTPUT` 이 명령값인지 측정값인지가 아직
`OI-28` 이라, *"`FORCE=0` 이 막았다"* 와 *"무부하라 0 이다"* 를 완전히 못 가른다.
반대로 **`~2.0` 이 나오면 강한 증거**이고, 그때는 `HTRFORCE 0 0` 이 권고가 아니라
**필수**가 되며 과열 차단이 `FORCELEVEL` 도 0 으로 쓰는 것이 정당해진다.
⭐ A5 가 `2.000` 딱이면 A4 의 `0.000` 도 함께 강해진다 -- 명령값을 보고하는 필드가
`FORCE=0` 에서 0 을 보고한다는 뜻이라 게이팅의 직접 증거가 된다.

#### B. 열적 확인 -- ⏳ **히터 연결 뒤 (SSO 설치 후)**

⛔ **B 는 히터가 물려 있어야 뜻이 있다.**  미연결 상태로 돌리면 온도가 안 오르는 것을
*"강제 출력이 안 나간다"* 로 오독한다.

⛔ **시작 전에 `[hk] interval` 을 내려라 (5초 권장).**  `HK` 는 **캐시를 읽는다** —
새 질의를 하지 않고 HK 루프가 마지막에 담아 둔 표본을 그대로 준다.  기본 60초로 두면:

* 3번의 *"30초 유지 — 오르는가"* 를 **표본 0~1개**로 판정하게 되고,
* 멈출 조건 *"1 K 이상 오르면"* 이 **최대 60초 늦게** 걸리며,
* ⛔ **2번의 판정이 통째로 무효가 된다** — `HTROUT` 도 같은 60초 캐시라 명령값이든
  측정값이든 **언제나 지연돼 보인다.**  그러면 `OI-28` 의 답이 계측 방식 때문에 미리
  정해진다.

기동 검사는 `1.0` 미만에서만 경고하므로 5초는 그냥 통과한다.  **끝나면 60 으로 되돌린다.**

**절차** (한 걸음씩, 각 걸음마다 `CCDTEMP`·`DMPTEMP` 를 본다)

⚠️ 히터 명령 다섯은 **즉답이 없다** (`Reply.noop()` → 컨트롤러 왕복 뒤 늦은 `DONE`).
응답이 안 왔다고 다시 치지 말 것.

| # | 명령 | 확인 |
|---|---|---|
| 1 | `HTRSET 0 <현재 목표온도>` | 히터 Enable 을 끈다.  ⛔ **`HTREN` 이라는 명령은 없다** — `HTRSET` 하나로 Enable+목표온도를 함께 받고 **인자가 정확히 둘**이라 `HTRSET 0` 만 치면 `Usage:` 로 거절된다.  현재 목표온도는 인자 없이 `HTRSET` 을 쳐서 되읽는다(`Enable=… Target=…`).  ⭐ 끄는 이유는 *"PID 와 강제가 겹쳐서"* 가 **아니다**(강제는 PID 를 **대체**한다) — **강제를 풀었을 때 PID 가 어떤 목표로 되살아나는지 알고 시작하려는 것**이다 |
| 2 | `HTRFORCE 1 1.0` | `HTROUT` 이 **1.0 V 부근**을 보고하나.  ⭐ 즉시 따라오면 명령값, 지연·오차가 있으면 측정값.  ⛔ **위의 `interval` 을 안 내렸으면 이 판정을 하지 마라** |
| 3 | 30초 유지 | `CCDTEMP`·`DMPTEMP` 가 **오르기 시작하는가** |
| 4 | `HTRFORCE 1 2.0` | 같은 관찰.  ⛔ **2.0 V 를 넘기지 않는다** |
| 5 | ⛔ **`HTRFORCE 0 0`** | 강제 해제 + **레벨까지 0 으로**.  `HTROUT` 이 0 으로 떨어지는지 확인 |
| 6 | `HTRSET <원래 Enable> <원래 목표온도>` | ⭐ **정상 제어 상태로 되돌린다.**  1번에서 적어 둔 값 그대로.  ⚠️ 이걸 빠뜨리면 DMP 가 PID 없이 남는다 |

⛔ **멈출 조건 — 하나라도 걸리면 즉시 `HTRFORCE 0 0`**

- `CCDTEMP` 또는 `DMPTEMP` 가 **1 K 이상 오르면** 즉시 중단한다.
- `HTROUT` 이 지시값보다 **크게** 나오면 즉시 중단한다 (강제 경로가 예상과 다르다).
- `HTROUT` 이 `NC` 로 오면 되읽기 경로가 없는 것이다 — 강제를 더 올리지 말고 `OI-25` 로 돌아간다.
- 진공(`DEWPRES`)이 흔들리면 중단한다 — 히터가 예상 밖 부하에 걸린 것이다.

⚠️ **되돌림을 반드시 확인할 것.**  `FORCE=0` 이면 출력은 0 V 다(위 전제) — 그래도
**레벨까지 `0` 으로 되돌리고** `HK` 로 `HTROUT=0` 을 눈으로 확인한 뒤 끝낸다.

⭐ **왜 레벨까지 쓰나** (기전을 정확히 적어 둔다 — 종전 문구가 틀렸다):

* console·remote 로는 **옛 전압이 되살아날 수 없다.**  `HTRFORCE` 는 인자가 정확히
  둘이라 `HTRFORCE 0` 만 치면 `Usage:` 로 거절되고, `set_force()` 가 `FORCE` 와
  `FORCELEVEL` 을 **늘 한 쌍으로** 쓴다.  다음 사람이 `HTRFORCE 1 …` 을 쳐도 그때
  레벨을 함께 주게 된다.
* 남는 창은 **아무도 Apply 를 안 누르고 ICG 도 재기동 안 한 사이**뿐이다.  그동안
  설정 메모리에 옛 레벨이 앉아 있고, 그 상태에서 **손 `WCONFIG` 로 `FORCE` 만** 1 로
  쓰면 그 값이 나간다.  레벨을 0 으로 두는 비용은 0 이고 그 창을 닫는다.
* ⚠️ `ArchonGUI` 의 Apply 버튼은 어느 것이든 **설정 전체를 다시 올린다**
  (`parseUI()` → `CLEARCONFIG` → `WCONFIG` 전량 → `APPLY…`, `ARCHONGUI_ANALYSIS.md:654`).
  그래서 GUI 를 거치면 우리가 쓴 값이 **GUI 위젯 값으로 덮인다** — 되돌아가는 것이
  아니라 *그 GUI 가 들고 있는 것*으로 바뀌는 것이라, 우리 ACF 와 같다는 보장이 없다.

⚠️ **`APPLYMOD` 가 MOD10 VCPU 를 재시작한다** (DevNote 11.18) — 이 절차를 도는 동안
`DEWPRES` 가 한동안 결측일 수 있다.  그것은 고장이 아니다.
