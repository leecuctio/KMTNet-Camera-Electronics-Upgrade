## 0단계 — 시작 전 준비물 ⚠️ **없으면 1단계가 막힌다**

### (a) RADIONODE 자격증명 — ⛔ **운영자만 할 수 있다** (콘솔 접근)

⭐ **2026-09-08 로 크게 줄었다** — 공개 매뉴얼(`oa.radionode365.com/apidoc/kr/`)을 읽고
코드를 실제 규약에 맞추면서 *"매뉴얼에서 옮겨 적어야 하는 것"* 이 사라졌다 (DevNote 11.44).

| # | 준비물 | 어디서 | 상태 |
|---|---|---|---|
| 1 | **계정 등급** — Open API 를 쓸 수 있는 유료회원사인가 | Radionode365 콘솔 | ✅ 확인됨 (`get_lst` 가 돈다) |
| 2 | **API KEY / SECRET** | `s2.radionode365.com` → 고객사 정보변경 → API Key/Secret | ⏳ 벤치 ini 에 적을 것 |
| 3 | **장치 `device_mac` 둘** | `channel/get_lst` 응답 (아래) | ⏳ 벤치 ini 에 적을 것 |
| 4 | ~~**base URL · 경로 · 헤더 이름**~~ | — | ✅ **필요 없다** — 코드가 안다 |
| 5 | ~~**SEND INTERVAL** 결정~~ | — | ✅ **필요 없다** — 응답의 `device_interval` 로 신선도 창이 잡힌다 |

⭐ **`device_mac` 은 이 한 줄로 다 보인다** (값은 저장소에 옮기지 말 것):

```bash
curl -d "api_key=<KEY>&api_secret=<SECRET>" -X POST \
     https://oa.radionode365.com/tp365/v1/channel/get_lst
```

⚠️ 계정에 **남의 장치가 많이 섞여 온다** (실물: `SSO-Top-ring`·`SSO-FSA` 등).  우리 것은
`device_model` 이 **`RN320-BTH`** 인 둘이다 — ⛔ `SSO-FSA` 는 이름도 채널 구성(T/RH)도
판박이라 잘못 적으면 **그럴싸한 값이 실려 못 알아챈다.**

⛔ **보안 토큰(`api_token`)은 쓰지 않는다.**  매뉴얼 경고: *"보안 토큰 설정 시 API KEY 의
사용 권한이 즉시 제거"* — 콘솔에서 그것을 켜면 폴링이 그날로 인증 실패로 죽는다.

⛔ **KEY/SECRET 실값을 저장소 `icg_archon.ini` 에 적지 말 것.**  한 번 커밋되면 이력 재작성 없이는
못 뺀다.  **벤치 설치본 `~/AIC/Config/icg_archon.ini` 에만** 적는다.  절차는 `README.md` 의
"Radionode 자격증명" 절.

⛔ **`stale_after` 가 재는 것은 장치의 표본시각이 아니라 우리가 폴링을 받은 시각이다** (2026-09-06 확인) -- `_store()` 가 그 자리에서 `time.monotonic()` 을 찍고, 응답의 시각 필드를 읽는 코드가 없다.  그래서 이 값이 잡는 것은 **장치 침묵이 아니라 폴링 실패**(인터넷·API 장애)뿐이고, `HKUDATE` 도 측정시각이 아니라 **마지막 폴링 성공 시각**이다.
✅ **세 문턱이 이제 서로 맞는다** (운영자 2026-09-08 · DevNote 11.44): `radionode.stale_after` **4000 초기값 → `device_interval` x3**(60s→180 · 600s→1800) → `hk.sensors()` 180 s 지평선은 **Radionode 면제** → science `hk_stale_after` **2000**.  ⛔ `HKUDATE` 는 **guide 유닛 측정값만** 기준이다 (Radionode 는 값만 싣고 시각 셈에서 빠진다).

⭐ `stale_after` 는 **SEND INTERVAL 의 약 3배**로 맞춘다 (현재 600 s = 3분 간격 전제 -- ⚠️ 3×180 s = 540 이지 600 이 아니다).  ④를 정하면
이 값도 함께 고친다 — 안 고치면 멀쩡한 표본을 낡았다고 버리거나, 낡은 값을 헤더에 싣는다.

### (b) 그 밖

- 벤치 네트워크에서 **인터넷이 되는가** — `openapi` 백엔드는 인터넷이 있어야 한다.  끊기면
  `HEBOX`/`FSATEMP`/`FSAHUM` 이 그동안 sentinel 이고, 운영자는 그 결측을 받아들이지 않는다(2026-09-04).
- guide 유닛 `10.0.0.162` 접속 · ACF **`KMTK_GUI_162_STA0201_R2618.acf`** 적용 여부.
- science 는 **`KMT?_SCI_*_R2611_*.acf`** 6장이 현행이다.
- ⭐ **장치 MAC / 시리얼** — 벤치 ini 의 `[radionode.hebox]`·`[radionode.fsa]` 에 적을 값.
  ⚠️ 자격증명과 **별개**다.  이것이 비면 3(`CONNECT`)은 통과하는데 4(`HK`)에서 값이
  계속 sentinel 로 남는다.  ✅ **이제 프로그램이 그 사실을 먼저 말한다** (2026-09-07,
  DevNote 11.42) — 기동 경고 · `RADIONODE STATUS` 의 `NoMAC=` · `CONNECT` 응답의
  `NoMAC=… (those cards stay sentinel)`, 그리고 **폴링이 그 장치를 아예 건너뛴다**
  (빈 `{mac}` URL 로 API 를 치면 쿼터만 깎이고 오진을 부른다).
  ⛔ **배포 ini 는 지금 둘 다 비어 있다** — 예행으로 확인했다.
- **`stale_after`** = 장치 SEND INTERVAL 의 **3배** 로 맞춘다 (0단계 (a) 4번에서 정한 값).

### (c) ⛔ 배포 ini 그대로면 **ICS 가 기동에서 멈춘다** (2026-09-06 전수 검토)

네 가지가 실기 기동 앞을 막거나 조용히 어긋난다.  **전부 코드로 확인했다.**

| # | 무엇 | 근거 | 해야 할 것 |
|---|---|---|---|
| 1 | ✅ **닫혔다 (2026-09-07, 운영자 지시)** | 종전엔 배포 `ics_archon.ini` 가 `require_xis = true` 인데 `xis_host` 가 **비어 있어** `xischeck.py:100` 이 `XisUnreachable` 을 던졌다 | 이제 배포 ini 가 **`xis_host = 127.0.0.1` · `xis_port = 6660`** 이다.  ⚠️ **허브가 다른 호스트면 그 IP 로 바꾼다** — 그대로 두면 로컬에 허브가 없을 때 기동이 멈춘다(`require_xis = false` 로 내리는 것이 그때의 탈출구다).  ⛔ 코드는 자동으로 직결로 안 넘어간다 (11.15 확정) |

| 4 | ⚠️ **짝이 안 맞는 ACF 는 `IP=` 까지 밀어 넣는다** | ACF 안에 `IP=10.0.0.162`(guide)·`IP=10.0.0.113`(science)가 있고, `apply_acf()` 는 **전 키를 `WCONFIG`** 한다 — `IP` 를 거르는 코드가 없다 | 유닛과 ACF 짝을 **적용 전에 눈으로** 대조한다.  ⚠️ `APPLYALL` 만으로 IP 가 바뀌지는 않는 것으로 보이나(`APPLYNET` 이 따로다) **확인된 바 없다** — `FLASHACTIVECONFIG`·`REBOOT` 가 뒤따르면 굳는다 |

⭐ **1·2 는 한 줄로 정리된다** — 배포 ini 는 이제 **둘 다 허브를 본다**(`127.0.0.1:6660`).

⚠️ 허브를 내린 동안은 콘솔의 `>NODE 메시지`(예 `>XIS HOSTS`)도 못 나간다.

## 1단계 — RADIONODE 자료획득 시험 ⭐ **실기 시험 첫 항목**

### 지금까지 선 것 · 안 선 것 (2026-09-07 정리)

운영자: *"Radionode 는 실기 시험 첫 단계로, 이것저것 시험해 보면서 정리해 나가자."*
아래는 **시험에 들어가기 전의 현황**이다 — 무엇이 이미 돌고, 무엇이 실기 응답을 봐야
정해지는지.

**무엇을 위한 것인가**: 헤더 카드 **셋** — `HEBOX`(전장박스 온도) · `FSATEMP`/`FSAHUM`
(FSA 내부 온·습도).  규격 5.8절이 이 셋을 **실측 계통**으로 규정한다.

⛔ **왜 클라우드를 거치나** — 장치(RN320-BTH)는 **LoRaWAN 이라 IP 스택이 없다.**
LAN 폴링이 원천적으로 불가하고, LoRa 게이트웨이를 거쳐 Tapaculo365 클라우드로만 간다.
그래서 접근이 **Open API 폴링**이고, endpoint 상세가 콘솔 로그인 뒤의 "OPENAPI 매뉴얼"
에만 있어 **URL·경로·인증 헤더 이름까지 ini 소관**이다.

| 백엔드 | 상태 | 무엇 |
|---|---|---|
| `off` | ✅ **기본값** | 아무것도 안 한다 — 세 키 결측 → 헤더 sentinel |
| `openapi` | ✅ 코드 완성 · ⏳ **실기 미검증** | Tapaculo365 를 `poll_period` 마다 폴링.  ⛔ 인터넷 필수.  **이번 시험의 대상** |
| `sim` | ✅ 됨 | 코드 상수 고정값.  ⭐ **헤더 경로로는 안 나간다** — 상수가 실측처럼 아카이브에 남으면 나중에 파일만 보고 못 가린다.  배선 확인용 |
| `local_lns` | ⏳ **자리만 있고 구현 없음** | 사설 LoRaWAN 서버(ChirpStack).  선행이 **운영자 액션 둘** — 게이트웨이 관리 접근 · 장치 가입 키(DevEUI/JoinEUI/AppKey) |

**이미 선 것**
- 폴러·캐시·신선도 판정 (`icg_archon/radionode.py`, 708줄) — `values_with_time()` 이
  표본시각을 함께 내므로 하류가 낡은 값을 낡은 것으로 판정한다
- 런타임 명령 `RADIONODE [status｜connect｜disconnect｜reconnect｜enable｜disable] [장치]`
  — ⭐ **인자 유무로 뜻이 갈린다**: 인자 없으면 **폴링 자체**, 장치 이름이 붙으면 **그 장치**
- HK 루프 배선 — `hk.py` 가 주기마다 `_sample` 에 담고 CSV·스냅샷·헤더로 흘린다
- 시험 `tests/test_icg_radionode.py`

**⛔ 안 선 것 — 그래서 이번 시험이 필요하다**
- **자격증명 둘**(`api_key`·`api_secret`)과 **`device_mac` 둘** — 콘솔 접근이라
  **코드가 대신 못 한다**.  0단계 (a).  ⭐ `base_url` 은 ini 에 실값이 들어 있고,
  `latest_path`·`key_header`·`secret_header` 는 **폐기됐다**(이 API 에 없는 자리다).
- **실기 응답 모양을 아무도 못 봤다** — `radionode.py` 스스로 PROVISIONAL 이라 적어 뒀다.
  원값 포맷(소수 자리·부호·단위)이 규격 `OI-16` 의 답이다
- **값 폐기 자리 넷** — 아래 "실험하면서 함께 볼 것"
- ⏳ `local_lns` — 인터넷이 끊기면 세 카드가 결측인데 **운영자는 그것을 받아들이지 않는다**
  (2026-09-04 확정).  ⚠️ 지금 길이 클라우드 하나뿐이라 **코드로는 못 막는다** —
  `stale_after` 를 늘리는 것은 결측을 없애는 게 아니라 **틀릴 수 있는 값으로 덮는 것**이라
  규격 5.0절 sentinel 의 정신에 어긋난다

**✅ 신선도 문턱 셋 -- 이제 맞는다** (2026-09-08 개정 · DevNote 11.44)

| 문턱 | 값 | 무엇 |
|---|---|---|
| `radionode.stale_after` | **4000 초기값 → `device_interval` x3** | 응답이 전송주기를 알려 주므로 **읽은 뒤 키별로** 잡힌다 (실물 60s→180 · 600s→**1800**) |
| `hk.sensors()` 지평선 | `[hk] interval` x3 = 180 s | ⭐ **Radionode 는 면제**다 -- 폴러가 자기 창으로 이미 걸렀다.  안 면제하면 주기가 긴 장치는 늘 sentinel |
| science `hk_stale_after` | **2000 s** (종전 300) | ⛔ 300 의 근거 *"icg 주기 60s 의 5배"* 가 **Radionode 를 안 셌다** |

⭐ **`stale_after` 가 재는 것도 바뀌었다** -- 종전에는 `_store()` 가 그 자리에서 찍어 *폴링
받은 시각*을 쟀고, 그래서 잡는 것이 *장치 침묵*이 아니라 *폴링 실패*뿐이었다.  이제는 응답의
**`ch_timestamp`(장치가 잰 시각, UTC epoch -- 실측 확인)** 를 쓴다.
⛔ **`HKUDATE` 는 guide 유닛 측정값만 기준**이다 -- Radionode 는 값만 싣고 시각 셈에서 빠진다
(운영자 2026-09-08).  ⚠️ **SEND INTERVAL 을 손으로 맞출 일이 없어졌다** -- API 가 알려 준다.



> ⛔⛔ **기동이 곧 전원 인가다** (2026-09-06 정정 — 종전 문구가 거짓이었다).
> `ArchonController.prepare()` 끝이 `if not self.powered: await self.power_on()` 이고,
> ICG 기동의 `_connect_controller()` → `guide.prepare()` 가 그것을 부른다.  즉
> **실기 백엔드로 `python3 -m icg_archon` 을 띄우는 순간 `CLEARCONFIG`+`WCONFIG`
> 전량+`APPLYALL`+`POWERON` 이 돈다** (`apply_acf = true`).
>
> ⭐ **그래서 1단계를 돌리는 길이 둘이다:**
>
> * **(가) 전원 없이** — `--backend sim` 으로 띄운다.  `SimGuideBackend` 라 컨트롤러
>   접속 자체가 없어 Radionode 배선만 가른다.  ⚠️ 헤더 경로는 못 본다.
> * **(나) 실기로** — [`icg_first_run.md`](icg_first_run.md) **0~2단계를 먼저**
>   마친다(배선 · probe · **Config 슬롯 대조**).  ⛔ 슬롯 대조를 건너뛰고 기동하면
>   `set_config` 가 엉뚱한 줄을 고쳐 `EXPTIME` 이 조용히 안 바뀐다.
>
> 아래 절차 1~5 는 헤더가 필요 없다 — 위 (가)면 전원 없이 그대로 돌릴 수 있다.
> ⛔ **헤더를 봐야 하는 항목(구 6·7·8)은 `1-B` 로 갈랐다** — 그것은 `go 1`,
> 곧 **첫 전원 인가**를 요구하므로 [`icg_first_run.md`](icg_first_run.md)
> **0~4단계를 먼저 마쳐야 한다**.

**닫히는 것**: 규격 `OI-16`(Radionode 원값 포맷) · 5.8절 *"원값 그대로 싣기"* 확정 · HK 5장 중
`HEBOX`/`FSATEMP`/`FSAHUM` 의 실기 경로.

### 절차

| # | 하는 것 | 기대 | 실측 |
|---|---|---|---|
| 1 | 벤치 ini 에 자격증명 4개를 적고 ICG 기동 | 기동 로그에 Radionode 폴러가 뜬다 | |

### 판정 (1단계)

- **통과**: 4 가 실값이고 5 에 원값 표기를 적어 왔다.
- **멈출 조건**
  - 3 에서 자격증명 거절 → 0단계 (a) 로 돌아간다.
  - ⭐ **3 은 통과했는데 4 가 계속 sentinel** → 0단계 (a) 로 통째로 돌아가지 말 것.
    장치 **MAC/시리얼**이 ini 의 `[radionode.hebox]`/`[radionode.fsa]` 와 맞는지,
    `stale_after` 가 **SEND INTERVAL 의 3배**인지부터 본다 (그 둘이 준비물 표에 없어
    실제로 여기서 막힌다).
  - 폴링이 아예 안 뜨면 `RADIONODE STATUS` 의 `backend=` 를 본다 — 기본이 `off` 다.

### ⛔ 히터 강제 출력 — 안전 봉투 (`OI-28` 실측용)

⚠️ **`HTRFORCE 1` 은 PID 를 우회한다** — `HEATERALIMIT`(25 V)은 **PID 모드 전용**이라
강제 모드에서는 안 걸린다.  즉 **온도와 무관하게 지시한 전압이 그대로 나간다.**
⭐ 코드에 운영 상한(`heater_force_max`)을 **일부러 두지 않았으므로**(값 미정, DevNote
11.14-(3)) **그 상한이 사는 자리는 이 문서뿐이다.**

⭐ **전제 — `FORCE=0` 이면 출력이 꺼진다 (0 V).**  근거 등급은 **운영자 확정
(2026-09-06)** 이다 — 매뉴얼(p.60-61)은 `FORCELEVEL` 의 범위(`0.000~25.000 V`)만 적고
*`FORCE=0` 일 때 레벨이 출력에 물리는지는 한 줄도 없다.*  ⚠️ 실측으로 확인된 것이
아니므로, 이 전제가 깨지는 관찰(예: `FORCE=0` 인데 `HTROUT` 이 0 이 아니다)이 나오면
**그 자리에서 멈추고 기록할 것.**

⭐ **자동 차단이 하나 생겼다** (2026-09-06 신설, `heater.OverTempGuard`) — 되먹임 센서
(`HEATERASENSOR` → `SENSORA`=`RTD9_DMP`)가 ACF 의 `SENSORAUPPERLIMIT`(현행 **50.0 °C**)를
넘으면 `FORCE`·`FORCELEVEL`·`ENABLE` 셋을 0 으로 쓴다.  ⚠️ **빠른 인터록이 아니다** —
판정이 HK 루프 주기로만 돌아 최대 `[hk] interval` 만큼 늦고, 50 °C 는 DMP 운전점
(−120 °C)에서 한참 위다.  **이 문서의 절차가 여전히 1차 방어선이다.**

⭐ **지금 히터가 안 붙어 있다** (운영자 2026-09-06) -- 그래서 둘로 가른다.  **A 는 지금
벤치에서 할 수 있고**(열이 갈 데가 없어 위험 0), B 는 히터를 연결한 뒤(SSO 설치 후)다.

#### A. 무부하 확인 -- ⭐ **지금 할 수 있다** (히터 미연결)

⭐ 운영자 착안: *"그냥 STATUS HEATEROUTPUT 을 보면 되지 않을까?"* -- 맞다.  부하가 없어도
`MOD10/HEATERAOUTPUT` 은 읽히므로 **`FORCE` 게이팅과 `OI-28` 을 같은 왕복으로 좁힌다.**

⚠️ `HK` 는 60초 캐시라 여기 쓰지 마라.  `archon STATUS` 로 직접 읽는다 -- 응답이 1800 B
에서 잘리므로 **전문은 `icg_archon.cmd` 로그**에서 본다.

| # | 명령 | 보는 것 | 실측 |
|---|---|---|---|
| A1 | `HTRSET` (인자 없이) | 현재 `Enable=…  Target=…` 을 **적어 둔다** (A7 복귀용) | |
| A2 | `HTRSET 0 <A1 의 목표온도>` | Enable 을 끈다.  인자는 **정확히 둘**이다 | |
| A3 | `HTRFORCE 0 2.0` | ⭐ **`FORCE=0` 인데 레벨만 2.0.**  `archon STATUS` 의 `MOD10/HEATERAOUTPUT` | |
| A4 | **판정** | `0.000` → `FORCE=0` 이 출력을 막는다 (운영자 이해와 일치) · **`~2.0` → ⛔ 막지 않는다** | |
| A5 | `HTRFORCE 1 2.0` | 같은 필드.  ⭐ **`2.000` 딱** 이면 명령값 쪽 · **`1.9xx`** 처럼 어긋나면 측정값 쪽 (`OI-28`) | |
| A6 | ⛔ `HTRFORCE 0 0` | `MOD10/HEATERAOUTPUT` 이 `0.000` 인지 확인 | |
| A7 | `HTRSET <A1 의 Enable> <A1 의 목표온도>` | 정상 제어로 복귀 | |

⚠️ **A4 의 `0.000` 은 약한 증거다.**  `HEATERAOUTPUT` 이 명령값인지 측정값인지가 아직
`OI-28` 이라, *"`FORCE=0` 이 막았다"* 와 *"무부하라 0 이다"* 를 완전히 못 가른다.
반대로 **`~2.0` 이 나오면 강한 증거**이고, 그때는 `HTRFORCE 0 0` 이 권고가 아니라
**필수**가 되며 과열 차단이 `FORCELEVEL` 도 0 으로 쓰는 것이 정당해진다.
⭐ A5 가 `2.000` 딱이면 A4 의 `0.000` 도 함께 강해진다 -- 명령값을 보고하는 필드가
`FORCE=0` 에서 0 을 보고한다는 뜻이라 게이팅의 직접 증거가 된다.

#### B. 열적 확인 -- ⏳ **히터 연결 뒤 (SSO 설치 후)**

⛔ **B 는 히터가 물려 있어야 뜻이 있다.**  미연결 상태로 돌리면 온도가 안 오르는 것을
*"강제 출력이 안 나간다"* 로 오독한다.

⛔ **시작 전에 `[hk] interval` 을 내려라 (5초 권장).**  `HK` 는 **캐시를 읽는다** —
새 질의를 하지 않고 HK 루프가 마지막에 담아 둔 표본을 그대로 준다.  기본 60초로 두면:

* 3번의 *"30초 유지 — 오르는가"* 를 **표본 0~1개**로 판정하게 되고,
* 멈출 조건 *"1 K 이상 오르면"* 이 **최대 60초 늦게** 걸리며,
* ⛔ **2번의 판정이 통째로 무효가 된다** — `HTROUT` 도 같은 60초 캐시라 명령값이든
  측정값이든 **언제나 지연돼 보인다.**  그러면 `OI-28` 의 답이 계측 방식 때문에 미리
  정해진다.

기동 검사는 `1.0` 미만에서만 경고하므로 5초는 그냥 통과한다.  **끝나면 60 으로 되돌린다.**

**절차** (한 걸음씩, 각 걸음마다 `CCDTEMP`·`DMPTEMP` 를 본다)

⚠️ 히터 명령 다섯은 **즉답이 없다** (`Reply.noop()` → 컨트롤러 왕복 뒤 늦은 `DONE`).
응답이 안 왔다고 다시 치지 말 것.

| # | 명령 | 확인 |
|---|---|---|
| 1 | `HTRSET 0 <현재 목표온도>` | 히터 Enable 을 끈다.  ⛔ **`HTREN` 이라는 명령은 없다** — `HTRSET` 하나로 Enable+목표온도를 함께 받고 **인자가 정확히 둘**이라 `HTRSET 0` 만 치면 `Usage:` 로 거절된다.  현재 목표온도는 인자 없이 `HTRSET` 을 쳐서 되읽는다(`Enable=… Target=…`).  ⭐ 끄는 이유는 *"PID 와 강제가 겹쳐서"* 가 **아니다**(강제는 PID 를 **대체**한다) — **강제를 풀었을 때 PID 가 어떤 목표로 되살아나는지 알고 시작하려는 것**이다 |
| 2 | `HTRFORCE 1 1.0` | `HTROUT` 이 **1.0 V 부근**을 보고하나.  ⭐ 즉시 따라오면 명령값, 지연·오차가 있으면 측정값.  ⛔ **위의 `interval` 을 안 내렸으면 이 판정을 하지 마라** |
| 3 | 30초 유지 | `CCDTEMP`·`DMPTEMP` 가 **오르기 시작하는가** |
| 4 | `HTRFORCE 1 2.0` | 같은 관찰.  ⛔ **2.0 V 를 넘기지 않는다** |
| 5 | ⛔ **`HTRFORCE 0 0`** | 강제 해제 + **레벨까지 0 으로**.  `HTROUT` 이 0 으로 떨어지는지 확인 |
| 6 | `HTRSET <원래 Enable> <원래 목표온도>` | ⭐ **정상 제어 상태로 되돌린다.**  1번에서 적어 둔 값 그대로.  ⚠️ 이걸 빠뜨리면 DMP 가 PID 없이 남는다 |

⛔ **멈출 조건 — 하나라도 걸리면 즉시 `HTRFORCE 0 0`**

- `CCDTEMP` 또는 `DMPTEMP` 가 **1 K 이상 오르면** 즉시 중단한다.
- `HTROUT` 이 지시값보다 **크게** 나오면 즉시 중단한다 (강제 경로가 예상과 다르다).
- `HTROUT` 이 `NC` 로 오면 되읽기 경로가 없는 것이다 — 강제를 더 올리지 말고 `OI-25` 로 돌아간다.
- 진공(`DEWPRES`)이 흔들리면 중단한다 — 히터가 예상 밖 부하에 걸린 것이다.

⚠️ **되돌림을 반드시 확인할 것.**  `FORCE=0` 이면 출력은 0 V 다(위 전제) — 그래도
**레벨까지 `0` 으로 되돌리고** `HK` 로 `HTROUT=0` 을 눈으로 확인한 뒤 끝낸다.

⭐ **왜 레벨까지 쓰나** (기전을 정확히 적어 둔다 — 종전 문구가 틀렸다):

* console·remote 로는 **옛 전압이 되살아날 수 없다.**  `HTRFORCE` 는 인자가 정확히
  둘이라 `HTRFORCE 0` 만 치면 `Usage:` 로 거절되고, `set_force()` 가 `FORCE` 와
  `FORCELEVEL` 을 **늘 한 쌍으로** 쓴다.  다음 사람이 `HTRFORCE 1 …` 을 쳐도 그때
  레벨을 함께 주게 된다.
* 남는 창은 **아무도 Apply 를 안 누르고 ICG 도 재기동 안 한 사이**뿐이다.  그동안
  설정 메모리에 옛 레벨이 앉아 있고, 그 상태에서 **손 `WCONFIG` 로 `FORCE` 만** 1 로
  쓰면 그 값이 나간다.  레벨을 0 으로 두는 비용은 0 이고 그 창을 닫는다.
* ⚠️ `ArchonGUI` 의 Apply 버튼은 어느 것이든 **설정 전체를 다시 올린다**
  (`parseUI()` → `CLEARCONFIG` → `WCONFIG` 전량 → `APPLY…`, `ARCHONGUI_ANALYSIS.md:654`).
  그래서 GUI 를 거치면 우리가 쓴 값이 **GUI 위젯 값으로 덮인다** — 되돌아가는 것이
  아니라 *그 GUI 가 들고 있는 것*으로 바뀌는 것이라, 우리 ACF 와 같다는 보장이 없다.

⚠️ **`APPLYMOD` 가 MOD10 VCPU 를 재시작한다** (DevNote 11.18) — 이 절차를 도는 동안
`DEWPRES` 가 한동안 결측일 수 있다.  그것은 고장이 아니다.

## 3.5단계 — `STOP`/`ABORT` 규약 실측 (P1·P2) [공통] — 2026-09-07 신설

운영자가 규약을 문면으로 확정했다 (2026-09-07).  **코드는 이미 그렇게 돼 있다** —
이 단계는 *"실기에서도 그런가"* 를 재고, **P1 의 규범을 정할 자료**를 얻는 것이다.

| | ICG (guide) | ICS (science) |
|---|---|---|
| **ABORT** | 노출 중지 + **`RESETTIMING`** 으로 끊고 `FlushFrame` **1회**.  ⛔ 영상을 읽지도 저장하지도 않는다 | 노출 중지.  ⛔ **flush 없음**.  영상을 읽지도 저장하지도 않는다 |
| **STOP** | 진행 중인 노출은 **저장까지 마치고** 멈춘다 (적분을 끊지 않는다) | 〃 |

⭐ **명령 이름은 `RESETTIMING` 이다** — `LOADTIMING` 은 타이밍 스크립트를 설정 메모리에서
코어로 올리는 **별개 명령**이고(DevNote 11.26), `TIMINGLOAD`/`TIMINGRESET` 이라는 이름은
Archon 명령표에 없다.

⭐ **그래서 `go`·`go 1` 수행 중 `STOP` 은 잴 것이 없다** — 막을 "다음" 이 없다.
`STOP` 시험은 **`go n`(n≥3)** 에서만 뜻이 있다.

⭐ **2단계와 함께 재면 한 번에 끝난다** — 2단계 표의 *"STOP 뒤 꼬리 flush"*(FRAME 불변 +
≈1.25 s)와 아래 `P2-1` 은 **같은 한 번의 `go n` + `stop`** 으로 둘 다 관측된다.  ICG 를
띄운 김에 A-1·A-4 도 이어서 하면 컨트롤러를 한 번만 세운다.

### P2 — `STOP` 때의 `EXPTIME` : ⏳ 미결이 아니라 **✅ 닫힌 것을 확인하는 항목**

⚠️ `SMC_CLAUDE.md` 의 *"정책 미정 P2"* 절은 **낡았다** (2026-08-24 기록).  2026-09-05 에
운영자 확정으로 뒤집혔다 (커밋 `93bfb08`, `Sequencer.stop_integration()` docstring 이 정본):
종전 구현은 레거시 `SoftStop=1` 처럼 카운트다운을 끊었는데, **짧아진 적분이 헤더
`EXPTIME` 에는 요청값으로 실려**(raw spec 5.4절) *"정상으로 보이는 오염 프레임"* 을 만들었다.
지금은 적분을 안 끊으므로 **저장되는 프레임은 언제나 온전한 노출**이고 `EXPTIME` 이 참이다.

| # | 하는 것 | 기대 | 실측 |
|---|---|---|---|
| P2-1 | `guideexp 2.0` → `go 5`, 3장째 독출 중에 `stop` | 진행 중 프레임까지 **저장**되고 그 뒤로 새 프레임이 안 걸린다.  ⭐ ICG 는 여기에 **꼬리 flush 1회(≈1.25 s)** 가 붙는다 (R2616 상수, DevNote 11.33) | |
| P2-2 | 저장된 마지막 파일의 헤더 | `EXPTIME` = 요청값(2.000).  ⛔ **그리고 그것이 참이어야 한다** — 직전 프레임과의 `DATE-OBS` 간격이 주기와 같으면 적분이 안 잘린 것이다 | |
| P2-3 | `go 1` 중에 `stop` | **아무 일도 안 일어난다** — 그 장은 그대로 저장된다.  ⚠️ 응답은 `DONE: STOP` 이다(거부가 아니다) | |
| P2-4 | 노출 중이 아닐 때 `stop` | `ERROR: STOP No integration in progress. Nothing to stop.` (레거시 문구 그대로) | |

⛔ **깨지면**: `EXPTIME` 이 요청값인데 `DATE-OBS` 간격이 그보다 짧으면 **적분이 잘린 것**이고,
2026-09-05 확정이 실기에서 안 도는 것이다.  그 프레임은 *"정상으로 보이는 오염 프레임"* 이라
자료로 쓰면 안 된다 — 그 자리에서 멈추고 기록할 것.

### P1 — `ABORT` 와 노출 번호 : ✅ **규범 ① 확정 · 코드 반영됨.  실기에서 확인한다**

⭐ **운영자 확정 2026-09-07: ① 재사용** — *"`ABORT` 는 번호를 안 먹는다."*  같은 프로세스
거동을 정본으로 삼고, **재시작도 그와 같게** 만들었다.  구현은 `State.rewind_expnum()` 을
두 시퀀서의 `ABORT` 경로가 부르는 것이고, 경위는 DevNote **11.40**.
⚠️ 그래서 아래 표의 **P1-3·P1-5·P1-6 기대값이 종전과 반대**다 — 옛 계획서를 들고 재면
"틀렸다" 고 읽는다.

**기전은 코드로 확정돼 있다** (2026-09-07 확인):

* `State.next_suffix()` 가 번호를 **쓰는 시점에** `_record_expnum()` 으로 파일에 적는다
  (`[paths] expnum_file`).  주석이 이유를 밝힌다 — *"`advance()` 까지 미루면 노출 중 죽었을 때
  그 번호가 기록되지 않아 재실행이 같은 번호를 다시 쓴다"*.
* `State.advance()` 는 **`EXPSTATUS=IDLE` 직후**에 돈다.  ⛔ **`ABORT` 는 거기까지 못 가서
  건너뛴다** → 같은 프로세스에서는 **번호가 재사용**된다.
* `State.load_expnum()` 은 *"마지막으로 쓴 번호 **+1**"* 부터 시작한다 → 되감기가 없으면
  재시작이 그 번호를 **건너뛴다**(영구 구멍).

**→ 비대칭은 이 셋의 곱이었다.**  ✅ 이제 `ABORT` 경로가 기록을 **한 칸 되감아**(`expnum - 1`)
재시작의 시작점을 같은 번호로 맞춘다.  ⛔ **`expnum` 자체는 안 바꾼다** — 같은 프로세스의
재사용은 이미 현행 거동이고, 되감기가 맞추는 것은 *기록*뿐이다.

| # | 하는 것 | 기대 (현행 코드) | 실측 |
|---|---|---|---|
| P1-1 | `expnum` 으로 현재 번호를 적어 둔다 → `go 1` → 독출 시작 뒤 `abort` | 파일이 **안 생긴다**.  ICG 는 flush 1회가 돈다 | |
| P1-2 | `expnum` 다시 | ⭐ **번호가 그대로**다 (advance 를 건너뛰었다) | |
| P1-3 | `expnum_file` 을 눈으로 (`~/AIC/icg_archon.expnum` 등) | ⭐ **되감긴 번호**(집었던 것보다 하나 앞)가 적혀 있다.  로그에 `ABORT -- 노출 번호 %06d 을 되감는다` 가 함께 뜬다 | |
| P1-4 | 이어서 `go 1` (재시작 없이) | 파일 이름이 **P1-1 과 같은 번호**를 쓴다 (재사용) | |
| P1-5 | 다시 `abort` → **프로그램 재시작** → `go 1` | ⭐ **같은 번호를 쓴다** — 종전에는 건너뛰었다.  이것이 규범 ① 이 산 자리다 | |
| P1-6 | 기동 로그 | `expnum 기록을 이어받는다 -- 마지막 %06d, 이번 %06d` 의 *이번* 이 P1-1 의 번호와 같다 (점프 없음) | |
| P1-7 | ⛔ **저장된 프레임은 안 건드린다** — `go 3` 으로 두 장을 받고 셋째 장에서 `abort` | 되감기가 **한 칸만** 물러나 둘째 장 번호가 산다.  재시작이 셋째 번호부터 | |

**✅ 운영자가 고른 것 — ① 재사용** (2026-09-07)

| 안 | 뜻 | 대가 |
|---|---|---|
| ⭐ **① 재사용** (같은 프로세스 거동을 정본으로) — **채택** | `ABORT` 는 번호를 안 먹는다.  재시작해도 그 번호부터 | `ABORT` 때 `expnum_file` 을 **되감는다**.  번호 공간에 구멍이 없어 아카이브가 연속이다 |
| ~~② 건너뜀~~ (재시작 거동을 정본으로) | `ABORT` 도 번호를 먹는다 | 번호에 **영구 구멍**이 남고, 나중에 보면 그 구멍이 `ABORT` 인지 사고인지 **구별할 수 없다** |

⭐ **①을 받친 것**: 이름 충돌 처리(D-016)가 이미 있어 번호가 겹쳐도 `resolve_pair_number()` 가
밀어내고 경고를 남긴다.  반대로 ②는 구멍의 뜻을 잃는다.

⛔ **`_record_expnum` 의 원래 목적은 안 깨진다** — 그 기록이 *쓰는 시점*에 도는 이유는
**노출 중 죽었을 때** 재실행이 같은 번호를 다시 쓰는 것을 막으려는 것이다.  되감기는
**명시적 `ABORT` 경로에서만** 불리므로 사고사는 종전대로 보호된다 (죽은 프로세스는
아무것도 되감지 못한다).  안전 조건은 `suffix_taken` 하나다 — `next_suffix()` 가 세우고
`advance()` 가 내리므로, 참이라는 것이 곧 *"번호를 집었고 그 프레임은 저장까지 못 갔다"* 다.

✅ **규범이 `ABORT` 밖으로 넓어졌다** (운영자 확대 2026-09-07, DevNote 11.41) —
**"파일이 안 생긴 프레임은 번호를 안 먹는다."**  되감는 경로가 다섯이다:

| 경로 | 되감나 |
|---|---|
| `ABORT` · `EXPENABLE OFF` (양쪽) | ✅ |
| ICS `BackendError` (`DMA WAIT TIMEOUT` 등) | ✅ |
| ICG `GuideBackendError` (사이클 실패) | ✅ |
| ICG **종료(shutdown)** | ✅ |
| ICG `except Exception` (내부 오류) | ⛔ **안 한다** — 우리 결함으로 죽어 상태를 모른다 |
| `NumberSpaceExhausted` | ⛔ **안 한다** — 되감아도 다음에 또 고갈.  ⚠️ ICS 는 그 갈래에서 `advance()` 를 명시적으로 불러 번호를 소비하고, ICG 는 안 부른다 |

⛔ **그래서 번호에 구멍이 보이면 뜻이 셋뿐이다** — ① ICG 내부 오류 ② 번호 공간 고갈
③ `expnum_file` 을 못 읽음.  셋 다 로그에 자국이 남으니 **구멍만 보고 추측하지 말 것.**

⚠️ **ICG·ICS 각각 재라** — 카운터가 독립이다 (`icg_archon.expnum` / `ics_archon.expnum`,
raw spec 9.2절 "카운터 독립").  ⭐ **`EXPENABLE OFF` 도 같은 되감기를 탄다** (ICG) — 그 경로가
`cancel()` 그대로라서다.  그 프레임도 안 나오므로 번호를 먹을 이유가 없다.

⭐ **시험은 이미 붙어 있다** — 셈은 `ics_sim/tests/test_expnum_persist.py` 의 되감기 절 여덟,
배선은 `ics_sim/tests/test_stop_abort.py` 둘 · `ics_archon/tests/test_icg_abort_flush.py` 둘.
그래서 이 단계에서 재는 것은 *"실기에서도 그런가"* 뿐이다.
